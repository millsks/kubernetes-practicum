Your Mac Lab: Colima and kind

Every lab in this course runs on a real Kubernetes cluster on your MacBook. This module builds that lab: a small Linux VM (Colima), a Docker engine inside it, and a three-node cluster made of containers (kind). Along the way you'll learn exactly where Docker stops and containerd starts, which explains half the "it works on my laptop" puzzles you'll meet later.

⏱ ~1.5 hoursPrerequisites: a Mac with Homebrew, comfort in a terminal

  • Explain why kind needs Docker but your Pods run on containerd, and move an image between them
  • Write a kind cluster config with two workers and a port mapping, and validate it before using it
  • Create, inspect, pause, and delete the primer cluster
  • Fix the most common local-cluster problems: inotify limits, memory, and port clashes

How this practicum works

Each module has four parts. You read an explanation with diagrams, tables, and small Python cells that run in your browser. You practice with graded exercises in the page. You build in a lab on your own machine. Then you check yourself with a quiz.

Python in the page

Cells run real CPython (Pyodide) in your browser. They use kubelab, a small library that reads YAML manifests, parses quantities like 128Mi, matches label selectors, and validates objects the way the API server would. It never talks to a cluster.

Labs on your Mac

Labs live in the kubernetes-practicum repository. pixi run start m00-lab1 copies a starter into work/; you edit it; pixi run grade m00-lab1 checks it.

No answer key

Labs ship without solutions. The checks are the specification, and the repository's CI proves every untouched starter fails, so a pass means you built it.

Live checks

Most checks are offline and run in seconds. Optional live checks (pixi run grade-live <lab>) apply your work to your kind cluster and wait for it to be healthy.

Colima: a Linux machine inside your Mac

Containers are a Linux feature: they're ordinary processes that the Linux kernel isolates with namespaces (what a process can see) and cgroups (how much CPU and memory it may use). macOS has a different kernel, so to run Linux containers you need a Linux kernel somewhere. Colima starts a lightweight Linux virtual machine and runs a Docker engine in it. Your docker CLI on macOS sends commands into that VM.

colima start --cpu 4 --memory 8 --disk 60 --vm-type vz --mount-type virtiofs
docker context use colima
docker info --format '{{.ServerVersion}} {{.Architecture}}'
FlagWhy this value
--cpu 4Three nodes plus the system Pods; four cores keeps rollouts snappy
--memory 8Enough for every stage, including Prometheus and Grafana in Stage 4. 6 GB is fine for Stages 1–2
--disk 60Images and volumes add up; the disk grows only as it's used
--vm-type vzApple's native hypervisor: faster and lighter than QEMU
--mount-type virtiofsFast file sharing between macOS and the VM

On an Apple Silicon Mac the VM is arm64, so nodes, Pods, and the images you build are arm64 too. Every image in this course is multi-architecture. For an amd64-only image, restart Colima with --vz-rosetta and pull with --platform linux/amd64.

Colima stops when your Mac sleeps or restarts. Before you read on: what do you expect happens to your kind cluster then? (The answer is in Day to day.)

Docker vs containerd: who runs what

This setup has two container runtimes, and they work at different layers. Getting this straight now saves hours later.

QuestionDocker (in Colima)containerd (in each kind node)
Who talks to it?You (docker) and kindThe kubelet, over CRI
What does it run?The node containers primer-control-plane, primer-worker…Your Pods' containers
Where do its images live?Colima's Docker image storeEach node's own store
How do images move?kind load docker-image NAME:TAG copies them into every nodeOr each node pulls from a registry itself
Inspect it withdocker ps, docker imagesdocker exec -it primer-worker crictl ps

The practical consequence: an image you docker build on your Mac is invisible to your Pods until you kind load it (or push it to a registry the nodes can reach). A Pod that can't find its image goes into ErrImagePull, then ImagePullBackOff. You'll diagnose exactly that in M02.

Use a pinned tag such as myapp:0.1.0 for images you load, and imagePullPolicy: IfNotPresent. With the tag :latest, Kubernetes defaults to Always and tries to pull from Docker Hub, ignoring the copy you loaded.

A kind cluster config

kind reads a small YAML file that describes the nodes. The course's primer cluster has one control-plane node and two workers, and publishes one port from the control-plane node to your Mac.

# kind-primer.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: primer
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30080   # a NodePort inside the cluster (used from Stage 2)
        hostPort: 8080         # http://*.localhost:8080 on your Mac
        protocol: TCP
  - role: worker
  - role: worker

Why three nodes on one laptop? Because scheduling, spreading replicas, draining a node, and "a node died" only mean something with more than one node. Each node is a container, so they're cheap.

Before you create a cluster, check the file. kubelab.check_kind_config returns a list of problems; an empty list means the file is valid. Try breaking it: change worker to workers, or give two mappings the same hostPort.

Create the primer cluster

kind create cluster --config kind-primer.yaml
kubectl cluster-info --context kind-primer
kubectl get nodes -o wide            # 1 control-plane + 2 workers, all Ready
docker ps --format '{{.Names}}'      # the nodes are just containers

kind create cluster does four things: it starts one Docker container per node from the kindest/node image (which bundles systemd, containerd, the kubelet, and kubeadm); it runs kubeadm init on the control plane and kubeadm join on the workers; it installs a network plugin (kindnet) and a storage provisioner; and it adds a context named kind-primer to ~/.kube/config and switches to it.

A context is a named pairing of a cluster, a user, and a default namespace. kubectl always talks to the current context, which matters as soon as you have more than one cluster.

kubectl config get-contexts           # * marks the current one
kubectl config use-context kind-primer
kind get clusters

Remember: if kubectl suddenly shows the wrong cluster (or none), check kubectl config current-context first.

How traffic reaches the cluster

The port mapping is a chain of three hops. Seeing it now makes Stage 2's networking much easier.

flowchart LR
  B[Browser or curl on your Mac] -->|localhost:8080| C[Colima port forward]
  C -->|VM port 8080| D[Docker publishes to primer-control-plane]
  D -->|node port 30080| S[A NodePort Service in the cluster]
  S --> P[Pods]

Until something in the cluster listens on NodePort 30080 (the gateway you install in Stage 2), localhost:8080 refuses connections. That's expected. Any name ending in .localhost resolves to your own machine in curl and in browsers, so later you'll use names like http://podinfo.localhost:8080 with no /etc/hosts edits.

The answer to the earlier question: when Colima stops, the node containers stop with it. colima start brings them back and the cluster resumes with its objects intact, because etcd's data lives on the control-plane container's disk.

Practice

Four short exercises on cluster configs and images. Each one uses kubelab or plain Python.

Write node_counts(yaml_text) that parses a kind config and returns a dict with the number of "control-plane" and "worker" nodes. A config with no nodes list has one control-plane node. Use kubelab.load_manifests and kubelab.node_roles.

Hint

Parse with kubelab.load_manifests(text)[0], then count the roles from kubelab.node_roles(config). Start both counts at zero.

Show solution
import kubelab

def node_counts(yaml_text):
    config = kubelab.load_manifests(yaml_text)[0]
    roles = kubelab.node_roles(config)
    return {"control-plane": roles.count("control-plane"), "worker": roles.count("worker")}

Write url_for(config, node_port, host="localhost") that returns the URL on your Mac that reaches node_port, such as "http://localhost:8080", using the config's extraPortMappings. Return None when no TCP mapping publishes that port. config is already a dict.

Hint

Loop over kubelab.port_mappings(config); each item has container_port, host_port, and protocol.

Show solution
import kubelab

def url_for(config, node_port, host="localhost"):
    for m in kubelab.port_mappings(config):
        if m.container_port == node_port and m.protocol == "TCP":
            return f"http://{host}:{m.host_port}"
    return None

Write needs_load(image, docker_images, node_images). It returns True when the image exists in Docker (on your Mac's side) but is missing from at least one node's containerd store, so kind load is required. node_images maps each node name to the set of images it has. If the image isn't in Docker at all, return False (there's nothing to load; build or pull it first).

Hint

Two conditions: the image is in docker_images, and any(image not in imgs for imgs in node_images.values()).

Show solution
def needs_load(image, docker_images, node_images):
    if image not in docker_images:
        return False
    return any(image not in images for images in node_images.values())

Write primer_gaps(yaml_text) that returns a list of what's missing for the course's cluster. Start with every problem from kubelab.check_kind_config, then add these exact messages when they apply: "name must be primer", "need exactly 2 workers", and "map node port 30080 to host port 8080" (a TCP mapping on a control-plane node). A perfect config returns [].

Hint

Build the list in the order the prompt gives. For the mapping, look for a PortMapping with role == "control-plane", container port 30080, host port 8080, and protocol TCP.

Show solution
import kubelab

def primer_gaps(yaml_text):
    config = kubelab.load_manifests(yaml_text)[0]
    gaps = list(kubelab.check_kind_config(config))
    if config.get("name") != "primer":
        gaps.append("name must be primer")
    if kubelab.node_roles(config).count("worker") != 2:
        gaps.append("need exactly 2 workers")
    wanted = kubelab.PortMapping("control-plane", 30080, 8080, "TCP")
    if wanted not in kubelab.port_mappings(config):
        gaps.append("map node port 30080 to host port 8080")
    return gaps

Quiz

Recap

  • Read and try in the page, build in a lab, grade with Pixi. Labs have no answer key.
  • Colima gives your Mac a Linux kernel and a Docker engine. Size it at 4 CPUs and 6–8 GB.
  • Docker runs kind's node containers; containerd inside each node runs your Pods. Move images with kind load docker-image.
  • The primer cluster: one control plane, two workers, NodePort 30080 published as localhost:8080.
  • Check configs before you use them; check the current context before you blame the cluster.
