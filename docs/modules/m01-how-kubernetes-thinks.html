How Kubernetes Thinks

Kubernetes isn't a tool that runs containers when you ask. It's a database of what you want, surrounded by control loops that keep making the world match it. Once that model clicks, every feature in the rest of the course (rollouts, autoscaling, GitOps) is the same idea applied to a different object.

The problem Kubernetes solves

Running one container on one machine is easy. Running hundreds across a fleet of machines raises questions that a single docker run never answers: which machine has room? What happens when a machine dies at 3 a.m.? How do you replace version 1 with version 2 without dropping requests? How do clients find a container whose IP keeps changing?

Kubernetes answers all of these with one design. You declare the end state you want ("three copies of this web server, version 2, reachable as web"). The system stores that declaration and runs controllers that notice any difference between what you declared and what exists, and fix it. Nobody, including you, scripts the steps.

Scheduling

Pick a node with enough CPU and memory, honouring your rules.

Self-healing

Replace containers and Pods that die, and Pods on nodes that die.

Rollouts

Move from one version to the next gradually, and roll back.

Discovery

Give a changing set of Pods one stable name and address.

Objects: spec and status

Everything you create is an object stored by the API server. Every object has the same outer shape:

apiVersion: apps/v1          # API group "apps", version "v1" (core objects are just "v1")
kind: Deployment             # the type
metadata:                    # identity: name, namespace, labels, annotations
  name: web
  namespace: default
  labels: {app: web}
spec:                        # what YOU want (desired state)
  replicas: 3
status:                      # what the cluster OBSERVED (written by controllers)
  readyReplicas: 2

You write

metadata (mostly) and spec. The spec is a request, not a command: "there should be three replicas".

Controllers write

status, plus metadata fields like uid, resourceVersion, generation, and ownerReferences.

Namespaces divide one cluster into named groups (default, kube-system, apps…). Most objects live in one; a few (Nodes, Namespaces themselves, PersistentVolumes) are cluster-wide. kubectl api-resources lists every kind and whether it's namespaced.

Declarative, not imperative

ImperativeDeclarative

Where the truth livesIn your shell historyIn a file you can review, diff, and version
kubectlrun, create, scale, set imageapply -f, diff -f, delete -f

kubectl apply sends your file to the API server, which merges it into the stored object. It's idempotent: applying the same file again is a no-op. That's what lets you keep manifests in Git and apply them on every change, which is all GitOps is (Stage 4).

Remember: imperative commands are fine for learning and emergencies. For anything you want to keep, write a file and apply it.

Controllers and the reconcile loop

A controller is a loop that owns one kind of object. Each pass it does three things:

  1. Observe: read the desired state (the spec) and the actual state (what exists).
  2. Diff: compute the difference.
  3. Act: take a step that makes the difference smaller, then go around again.

Step through a ReplicaSet controller handling a deleted Pod, a scale-up, a dead node, and a scale-down:

Kubernetes controllers are level-triggered: they act on the current state ("there are 4, there should be 5"), not on the event that caused it ("a Pod was deleted"). If a controller crashes and misses ten events, it doesn't matter: when it comes back it compares state again and does the right thing. That's the source of Kubernetes' self-healing.

An edge-triggered system reacts to each event once. What goes wrong if it misses the "Pod deleted" event while it's restarting? Why can't that happen to a level-triggered loop?

Controllers stack. A Deployment controller manages ReplicaSets; a ReplicaSet controller manages Pods; the scheduler places Pods; the kubelet runs them. Each owns one level and records ownership in metadata.ownerReferences, which is also how garbage collection works: delete a Deployment and its ReplicaSets and Pods are deleted after it.

Notice that nobody calls anybody. Each component watches the API for its own kind of work, does it, and writes the result back. You can watch the same story in the event stream:

Practice

Five exercises on reconciling, API groups, rollout status, ownership, and grouping Pods.

Write reconcile_step(desired, actual) that returns a tuple (action, count): ("create", n) when there are too few, ("delete", n) when there are too many, and ("none", 0) when they match. Negative desired is invalid: raise ValueError.

Hint

Compute diff = desired - actual once and branch on its sign.

Show solution
def reconcile_step(desired, actual):
    if desired < 0:
        raise ValueError("desired must not be negative")
    diff = desired - actual
    if diff > 0:
        return ("create", diff)
    if diff < 0:
        return ("delete", -diff)
    return ("none", 0)

Write split_api_version(api_version) that returns (group, version). Core objects have an empty group: "v1" gives ("", "v1"), while "apps/v1" gives ("apps", "v1") and "networking.k8s.io/v1" gives ("networking.k8s.io", "v1").

Hint

str.rpartition("/") returns ("", "", "v1") when there's no slash.

Show solution
def split_api_version(api_version):
    group, _, version = api_version.rpartition("/")
    return (group, version)

A Deployment's status can lag behind its spec. Write rollout_complete(deploy) that returns True only when the controller has seen the latest spec (status.observedGeneration >= metadata.generation) and status.updatedReplicas, status.readyReplicas, and status.replicas all equal spec.replicas. Missing status fields count as 0. This is roughly what kubectl rollout status waits for.

Hint

kubelab.dig(deploy, "status.readyReplicas", 0) reads a nested field with a default.

Show solution
import kubelab

def rollout_complete(deploy):
    want = kubelab.dig(deploy, "spec.replicas", 1)
    if kubelab.dig(deploy, "status.observedGeneration", 0) < kubelab.dig(deploy, "metadata.generation", 0):
        return False
    fields = ("updatedReplicas", "readyReplicas", "replicas")
    return all(kubelab.dig(deploy, f"status.{f}", 0) == want for f in fields)

Write owner_chain(objects, kind, name) that starts at one object and follows the first metadata.ownerReferences entry upward, returning ["Pod/web-7d9f-x2", "ReplicaSet/web-7d9f", "Deployment/web"]. Stop when an object has no owner, or when the owner isn't in objects.

Hint

Build a dict keyed by (kind, name) first, then loop while the current object has an owner you can look up.

Show solution
def owner_chain(objects, kind, name):
    index = {(o["kind"], o["metadata"]["name"]): o for o in objects}
    chain = []
    current = index.get((kind, name))
    while current is not None:
        chain.append(f"{current['kind']}/{current['metadata']['name']}")
        owners = current["metadata"].get("ownerReferences") or []
        if not owners:
            break
        current = index.get((owners[0]["kind"], owners[0]["name"]))
    return chain

Given Pods as returned by kubectl get pods -o json (items only), write pods_by_node(pods) returning a dict of node name to a sorted list of Pod names. Pods without spec.nodeName haven't been scheduled: put them under "<pending>".

Hint

Use dict.setdefault(node, []).append(name), then sort each list.

Show solution
import kubelab

def pods_by_node(pods):
    groups = {}
    for pod in pods:
        node = kubelab.dig(pod, "spec.nodeName") or "<pending>"
        groups.setdefault(node, []).append(pod["metadata"]["name"])
    return {node: sorted(names) for node, names in groups.items()}

Quiz

Recap

  • The API server is the front door; etcd stores state; the scheduler places Pods; controllers reconcile; the kubelet runs containers on each node.
  • Every object is apiVersion, kind, metadata, spec (you) and status (the system).
  • Declarative apply is idempotent: the file is the truth.
  • Controllers observe, diff, and act, level-triggered, which is why the cluster heals itself.
  • Nobody calls anybody: components watch the API and write back what they did. Events tell the story.
