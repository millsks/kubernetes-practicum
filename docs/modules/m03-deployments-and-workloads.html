Deployments and Workloads

You almost never create Pods yourself. You create a controller that creates them, replaces them when they die, and swaps them for a new version without dropping traffic. This module covers the Deployment, the controller you'll use most, in depth, then the other workload kinds and when each one fits.

Why controllers

A bare Pod has no guardian. If it crashes, the kubelet restarts its containers in place, but if the Pod is deleted or its node dies, it's simply gone. A ReplicaSet fixes that: it keeps a number of identical Pods running, using the reconcile loop you met in M01. A Deployment sits on top and manages ReplicaSets, one per version of your Pod template, so it can move you from one version to the next.

Labels and selectors

Labels are key/value pairs on any object: app.kubernetes.io/name: podinfo, tier: front. A selector is a query over labels. Controllers find "their" Pods by selector, not by name, which is why the selector and the template's labels must agree.

selector:
  matchLabels: {app.kubernetes.io/name: podinfo}       # every listed label must equal
  matchExpressions:                                    # and every expression must hold
    - {key: tier, operator: In, values: [front, edge]}
    - {key: canary, operator: DoesNotExist}
RuleWhy
spec.selector must match spec.template.metadata.labelsOtherwise the controller couldn't see the Pods it creates; the API rejects it
A Deployment's selector is immutableChanging it would orphan every existing Pod. To change it, create a new Deployment
Two controllers must not select the same PodsThey'd fight, each deleting Pods the other created. Include a distinguishing label
Label values are stringsWrite version: "2", not version: 2

A production-shaped Deployment

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: podinfo
  labels: {app.kubernetes.io/name: podinfo}
  annotations:
    kubernetes.io/change-cause: "podinfo 6.7.0"   # shown by rollout history
spec:
  replicas: 4
  revisionHistoryLimit: 5            # old ReplicaSets kept for rollback
  minReadySeconds: 5                 # a new Pod must stay Ready this long to count
  progressDeadlineSeconds: 120       # mark the rollout failed if stuck this long
  selector:
    matchLabels: {app.kubernetes.io/name: podinfo}
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                    # at most 1 Pod above replicas during a rollout
      maxUnavailable: 0              # never fewer than 4 ready
  template:
    metadata:
      labels: {app.kubernetes.io/name: podinfo}
    spec:
      securityContext: {runAsNonRoot: true, runAsUser: 10001, seccompProfile: {type: RuntimeDefault}}
      containers:
        - name: app
          image: ghcr.io/stefanprodan/podinfo:6.7.0
          ports: [{containerPort: 9898, name: http}]
          readinessProbe: {httpGet: {path: /readyz, port: http}}
          livenessProbe: {httpGet: {path: /healthz, port: http}}
          resources:
            requests: {cpu: 50m, memory: 64Mi}
            limits: {memory: 128Mi}
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: {drop: [ALL]}

Notice what's not here: no Pod names, no node names. The Deployment describes a template and a count. Everything else follows.

Rolling updates

Change anything in spec.template (the image, an env var, a label) and the Deployment starts a rollout. Two numbers bound it:

SettingMeaningPercentages roundDefault
maxSurgeHow many Pods may exist above replicasUp25%
maxUnavailableHow many may be missing from replicasDown25%

So during a rollout: total Pods ≤ replicas + maxSurge, and ready Pods ≥ replicas − maxUnavailable. Both can't be zero, or the rollout could never take a step.

Try maxSurge: 0, maxUnavailable: 1 (no extra capacity: good when the cluster is full), then 25% and 25% with 10 replicas (the defaults), then 0 and 0.

Two fields make rollouts safer. minReadySeconds requires a new Pod to stay Ready for a while before it counts as available, which catches apps that pass one readiness check and then crash. progressDeadlineSeconds marks the rollout as failed (Progressing=False, reason ProgressDeadlineExceeded) if it makes no progress for that long. Kubernetes does not roll back on its own; your pipeline or you do that.

With maxUnavailable: 0, you push an image tag that doesn't exist. What happens to traffic? What does kubectl get rs show? Check your answer in the lab.

Driving rollouts

ActionCommand
Change the image (starts a rollout)kubectl set image deploy/podinfo app=ghcr.io/stefanprodan/podinfo:6.7.1
Watch itkubectl rollout status deploy/podinfo (exits non-zero if the deadline passes)
Record whykubectl annotate deploy/podinfo kubernetes.io/change-cause="6.7.1" --overwrite
Historykubectl rollout history deploy/podinfo
Roll back one revision, or to a specific onekubectl rollout undo deploy/podinfo, --to-revision=2
Batch several edits into one rolloutkubectl rollout pause deploy/podinfo … edit … kubectl rollout resume deploy/podinfo
Restart every Pod (e.g. after a Secret changed)kubectl rollout restart deploy/podinfo
Scale (doesn't create a revision)kubectl scale deploy/podinfo --replicas=6

A rollback is just another rollout: the Deployment copies an old ReplicaSet's template back and gives it a new revision number. Scaling never creates a revision, because replicas isn't part of the template.

kubectl rollout restart works by adding a timestamp annotation to the template. That's a template change, so it's a normal rolling update with all its safety.

The Recreate strategy

strategy: {type: Recreate} deletes every old Pod first, then creates the new ones. There is downtime between the two. Use it only when two versions must never run at once: an app that holds an exclusive lock, or a schema change old code can't survive. For everything else, use RollingUpdate and make your app tolerate a short overlap.

Jobs and CronJobs

# cronjob.yaml: print the date every five minutes
apiVersion: batch/v1
kind: CronJob
metadata: {name: ticker}
spec:
  schedule: "*/5 * * * *"             # minute hour day-of-month month day-of-week
  timeZone: America/Chicago           # otherwise the controller's time zone (usually UTC)
  concurrencyPolicy: Forbid           # skip a run if the last one is still going
  startingDeadlineSeconds: 120        # give up on a missed run after 2 minutes
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      backoffLimit: 2                 # retries before the Job is marked failed
      activeDeadlineSeconds: 60       # kill a run that takes longer
      ttlSecondsAfterFinished: 3600   # clean up finished Jobs
      template:
        spec:
          restartPolicy: OnFailure    # Jobs need OnFailure or Never
          containers:
            - name: tick
              image: busybox:1.36
              command: ['sh', '-c', 'date; echo hello from $(hostname)']
FieldWhat it controls
completions / parallelismHow many successful Pods a Job needs, and how many run at once
backoffLimitFailures allowed before the Job fails (default 6)
activeDeadlineSecondsWall-clock limit for the whole Job
concurrencyPolicyAllow (default), Forbid, or Replace the running Job
restartPolicyOnFailure retries in the same Pod; Never makes a new Pod per attempt (keeps the failed ones for logs)
 
kubectl create job once --from=cronjob/ticker    # run a CronJob now
kubectl get jobs,pods -l job-name=once
kubectl logs job/once

Practice

Five exercises on rollout maths, selectors, choosing controllers, and history.

Without using kubelab.rollout_bounds, write bounds(replicas, max_surge, max_unavailable) returning (max_pods, min_ready). Each setting is an int or a string like "25%"; percentages of replicas round up for surge and down for unavailable. The tests compare you with kubelab.

Hint

Write a helper that turns "25%" into replicas * 25 / 100 and rounds with math.ceil or math.floor, and turns ints into themselves.

Show solution
import math

def resolve(value, replicas, up):
    text = str(value)
    if text.endswith("%"):
        exact = replicas * float(text[:-1]) / 100
        return math.ceil(exact) if up else math.floor(exact)
    return int(text)

def bounds(replicas, max_surge, max_unavailable):
    surge = resolve(max_surge, replicas, True)
    unavailable = resolve(max_unavailable, replicas, False)
    return replicas + surge, replicas - unavailable

Two Deployments fight when one's selector matches the other's Pod template labels. Write overlaps(deployments) returning a sorted list of (a, b) name pairs (a < b) where either selector matches the other's template labels. Use kubelab.selector_matches.

Hint

Loop over every pair with two indices i < j and check both directions.

Show solution
import kubelab

def overlaps(deployments):
    def parts(d):
        return d["metadata"]["name"], d["spec"]["selector"], d["spec"]["template"]["metadata"]["labels"]
    found = []
    for i, a in enumerate(deployments):
        for b in deployments[i + 1:]:
            name_a, sel_a, labels_a = parts(a)
            name_b, sel_b, labels_b = parts(b)
            if kubelab.selector_matches(sel_a, labels_b) or kubelab.selector_matches(sel_b, labels_a):
                found.append(tuple(sorted((name_a, name_b))))
    return sorted(found)

Write choose(needs) that returns the controller kind for a workload described by a dict with boolean keys stable_identity, every_node, runs_to_completion, and an optional schedule string. Precedence: a schedule means "CronJob"; otherwise runs-to-completion means "Job"; otherwise every-node means "DaemonSet"; otherwise stable identity means "StatefulSet"; otherwise "Deployment". Missing keys are false.

Hint

A chain of if statements in the given order, using needs.get(key).

Show solution
def choose(needs):
    if needs.get("schedule"):
        return "CronJob"
    if needs.get("runs_to_completion"):
        return "Job"
    if needs.get("every_node"):
        return "DaemonSet"
    if needs.get("stable_identity"):
        return "StatefulSet"
    return "Deployment"

history is a list of revision numbers kept by a Deployment (for example [2, 4, 5]; old ones were pruned by revisionHistoryLimit). Write undo_target(history, to_revision=None): with no to_revision, return the revision just before the newest; otherwise return to_revision if it's in history. Raise ValueError when there's nothing to roll back to or the revision isn't kept.

Hint

Sort the history; the target is ordered[-2].

Show solution
def undo_target(history, to_revision=None):
    if to_revision is not None:
        if to_revision not in history:
            raise ValueError(f"revision {to_revision} is not in the history")
        return to_revision
    ordered = sorted(history)
    if len(ordered) < 2:
        raise ValueError("no previous revision to roll back to")
    return ordered[-2]

Write cronjob_for(name, schedule, image, command) returning a CronJob dict that kubelab.check_object accepts, with concurrencyPolicy: Forbid, backoffLimit: 2, restartPolicy: OnFailure, and one container named "task".

Hint

Copy the nesting from the cronjob.yaml above: spec.jobTemplate.spec.template.spec.

Show solution
def cronjob_for(name, schedule, image, command):
    pod = {"restartPolicy": "OnFailure", "containers": [{"name": "task", "image": image, "command": command}]}
    return {
        "apiVersion": "batch/v1",
        "kind": "CronJob",
        "metadata": {"name": name},
        "spec": {
            "schedule": schedule,
            "concurrencyPolicy": "Forbid",
            "jobTemplate": {"spec": {"backoffLimit": 2, "template": {"spec": pod}}},
        },
    }

Quiz

Recap

  • Deployments manage ReplicaSets (one per template version), which manage Pods. Selectors tie them together and must match the template's labels, without overlapping other controllers.
  • Rolling updates keep total ≤ replicas + maxSurge (rounded up) and ready ≥ replicas − maxUnavailable (rounded down).
  • minReadySeconds and progressDeadlineSeconds make rollouts honest; rollbacks are new revisions made from old templates.
  • Pick by need: Deployment (stateless), StatefulSet (identity and disks), DaemonSet (per node), Job (finish), CronJob (schedule).
  • Jobs need OnFailure or Never; CronJobs want a time zone, a concurrency policy, deadlines, and history limits.
