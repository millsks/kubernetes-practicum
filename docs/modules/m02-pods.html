Pods

The Pod is the smallest thing Kubernetes schedules: one or more containers that share a network address and storage, placed together on one node. Every higher-level object (Deployments, Jobs, StatefulSets) exists to create and replace Pods. Get Pods right, with health probes, resources, and security, and everything built on them behaves.

⏱ ~2.5 hoursPrerequisites: M01 How Kubernetes Thinks

  • Choose between startup, readiness, and liveness probes, and avoid the classic probe mistakes

  • Write a Pod that meets the restricted Pod Security Standard
  • Debug a Pod systematically with describe, logs, exec, port-forward, and ephemeral containers

What a Pod is

A Pod wraps one or more containers that are always scheduled together, on the same node. They share:

  • One network namespace: one IP address and one port space. Containers in a Pod reach each other on localhost, so two of them can't both listen on 8080.
  • Volumes declared on the Pod, which any container can mount.
  • A lifecycle: the Pod is created, runs, and is deleted as a unit.

A Pod you create directly (a bare Pod) is never recreated if it or its node dies. You'll use bare Pods in this module to learn; real workloads use a controller (M03).

Your first Pod

The course uses podinfo, a tiny Go web app built for Kubernetes demos. It has health endpoints, a version page, and switches to make it misbehave on purpose.

# pod.yaml: the minimum
apiVersion: v1
kind: Pod
metadata:
  name: podinfo
  labels: {app.kubernetes.io/name: podinfo}
spec:
  containers:
    - name: app
      image: ghcr.io/stefanprodan/podinfo:6.7.1
      ports: [{containerPort: 9898, name: http}]
kubectl apply -f pod.yaml
kubectl get pod podinfo -o wide -w        # Ctrl-C once it's Running
kubectl describe pod podinfo | tail -15   # the Events tell the story
kubectl port-forward pod/podinfo 9898:9898 &
curl -s localhost:9898 | head
kill %1

Names matter: metadata.name must be a DNS-1123 subdomain (lowercase letters, digits, - and .), container names and port names must be DNS labels, and port names are at most 15 characters. kubelab.check_object enforces the same rules as the API server.

Lifecycle: phases, states, restarts

Pod phase

PendingAccepted, but not running yet: waiting to be scheduled, pulling images, or mounting volumes
RunningBound to a node; at least one container running or restarting
SucceededEvery container exited 0 and won't restart
FailedEvery container stopped, at least one with an error
UnknownThe node stopped reporting

Container state

WaitingNot running yet, with a reason: ContainerCreating, ImagePullBackOff, CrashLoopBackOff…
RunningExecuting
TerminatedExited, with an exit code and a reason such as Completed, Error, or OOMKilled

spec.restartPolicy decides what the kubelet does when a container exits: Always (the default, required for Deployments), OnFailure, or Never (both for Jobs). Restarts back off exponentially (10 s, 20 s, 40 s… up to five minutes), and while waiting the container shows CrashLoopBackOff. The restart happens inside the same Pod on the same node; it isn't rescheduled.

Health probes

A running process isn't necessarily a healthy one. Probes let the kubelet ask your app how it's doing.

ProbeQuestion it answersOn failureClassic mistake
startupProbeHas the app finished starting?Keeps checking; the other probes wait until it passesMissing on slow starters, so liveness kills them mid-boot
readinessProbeCan it take traffic right now?Removed from Service endpoints; not restartedOmitting it, so traffic arrives before the app can serve
livenessProbeIs the process wedged?Container is restartedChecking the database here: one DB blip restarts every replica at once
 
    - name: app
      image: ghcr.io/stefanprodan/podinfo:6.7.1
      ports: [{containerPort: 9898, name: http}]
      startupProbe:                          # up to 30 × 2s = 60s to boot
        httpGet: {path: /healthz, port: http}
        failureThreshold: 30
        periodSeconds: 2
      readinessProbe:
        httpGet: {path: /readyz, port: http}
        periodSeconds: 5
      livenessProbe:
        httpGet: {path: /healthz, port: http}
        periodSeconds: 10
        failureThreshold: 3

Probe handlers are httpGet (a 2xx or 3xx counts as success), tcpSocket, exec (exit 0 is success), and grpc. Refer to ports by name (port: http) so changing the number in one place can't break the probe.

Remember: liveness checks this process only. Readiness can consider whether the app can do useful work. Startup protects slow boots.

Requests, limits, and QoS

RequestLimit
Used byThe scheduler, to place the Pod (the node must have this much unreserved)The kernel (cgroups), at runtime
CPU above itAllowed if the node has spare CPUThrottled: slower, never killed
Memory above itAllowed until the node runs short, then evicted firstOOMKilled: exit code 137

Quantities have units. CPU is in cores: 250m is a quarter of a core ("milli"). Memory is in bytes: 128Mi is 128 × 220 (binary), while 128M is 128 × 106 (decimal), about 5% smaller.

From requests and limits, the kubelet assigns a QoS class that decides who is evicted first when a node runs out of memory:

QoS classWhenEvicted
GuaranteedEvery container has CPU and memory limits, and requests equal limitsLast
BurstableAt least one request or limit is set, but not GuaranteedMiddle
BestEffortNo requests or limits at allFirst

A good default for web apps: set CPU and memory requests to typical usage, set a memory limit, and think twice before a CPU limit. CPU limits cause throttling, which shows up as mysterious latency spikes even when the node is idle.

Init containers and native sidecars

Init containers run to completion, one after another, before the app containers start. Use them to wait for a dependency, run a migration, or render a config file. A native sidecar (stable since Kubernetes 1.33) is an init container with restartPolicy: Always: it starts before the app, keeps running beside it, and stops after it, which is exactly what log shippers and proxies need.

spec:
  initContainers:
    - name: wait-for-db                 # classic init: must exit 0 before the app starts
      image: busybox:1.36
      command: ['sh', '-c', 'until nc -z db 5432; do echo waiting; sleep 2; done']
    - name: log-shipper                 # native sidecar: keeps running
      image: busybox:1.36
      restartPolicy: Always
      command: ['sh', '-c', 'tail -F /logs/app.log']
      volumeMounts: [{name: logs, mountPath: /logs}]
  containers:
    - name: app
      image: busybox:1.36
      command: ['sh', '-c', 'while true; do date >> /logs/app.log; sleep 1; done']
      volumeMounts: [{name: logs, mountPath: /logs}]
  volumes:
    - name: logs
      emptyDir: {}

While init containers run, kubectl get pod shows Init:0/2. If one keeps failing, the Pod shows Init:CrashLoopBackOff; read it with kubectl logs POD -c wait-for-db.

Security context: the restricted standard

By default a container may run as root and keep several Linux capabilities. Kubernetes defines three Pod Security Standards: privileged, baseline, and restricted. Write everything to restricted:

spec:
  securityContext:                       # Pod level
    runAsNonRoot: true
    runAsUser: 10001                     # numeric: needed when the image's USER is a name
    seccompProfile: {type: RuntimeDefault}
  containers:
    - name: app
      securityContext:                   # container level
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: {drop: [ALL]}

runAsNonRoot: true alone fails with CreateContainerConfigError if the image declares a non-numeric user (such as USER app), because the kubelet can't prove the name isn't root. Add a numeric runAsUser.

kubelab.warnings flags what a manifest is missing. Fix the Pod below until the only warning left is the one about it being a bare Pod.

Practice

Five exercises on quantities, probes, hardening, and diagnosis.

Write millicores(quantity) that converts a CPU quantity to whole millicores: "250m" → 250, "1.5" → 1500, 2 → 2000. Round to the nearest integer.

Hint

kubelab.parse_cpu returns cores as a float.

Show solution
import kubelab

def millicores(quantity):
    return round(kubelab.parse_cpu(quantity) * 1000)

Write headroom(container) that returns how many bytes a container may grow above its memory request before it's OOM-killed: limit minus request. Return None when there's no memory limit (no ceiling). A missing request counts as equal to the limit.

Hint

Read the two values with .get() and convert with kubelab.parse_memory.

Show solution
import kubelab

def headroom(container):
    resources = container.get("resources") or {}
    limit = (resources.get("limits") or {}).get("memory")
    if limit is None:
        return None
    request = (resources.get("requests") or {}).get("memory", limit)
    return kubelab.parse_memory(limit) - kubelab.parse_memory(request)

Write broken_probes(container) that returns a sorted list of the probe names ("startupProbe", "readinessProbe", "livenessProbe") whose httpGet or tcpSocket port is a name that no ports[].name in the container defines. Numeric ports are always fine.

Hint

Collect the named ports into a set first. A port is a name when it's a str that isn't all digits.

Show solution
def broken_probes(container):
    names = {p.get("name") for p in container.get("ports", []) if p.get("name")}
    broken = []
    for probe in ("startupProbe", "readinessProbe", "livenessProbe"):
        spec = container.get(probe) or {}
        for handler in ("httpGet", "tcpSocket"):
            port = (spec.get(handler) or {}).get("port")
            if isinstance(port, str) and not port.isdigit() and port not in names:
                broken.append(probe)
    return sorted(broken)

Write harden(pod) that returns a new Pod dict (don't modify the argument) that meets the restricted standard: at Pod level runAsNonRoot: true, runAsUser: 10001, and seccompProfile.type: RuntimeDefault; on every container allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, and capabilities.drop: ["ALL"]. Keep any settings that are already there.

Hint

Start with copy.deepcopy(pod), then use setdefault("securityContext", {}) and update().

Show solution
import copy

def harden(pod):
    out = copy.deepcopy(pod)
    spec = out["spec"]
    spec.setdefault("securityContext", {}).update(
        {"runAsNonRoot": True, "runAsUser": 10001, "seccompProfile": {"type": "RuntimeDefault"}})
    for container in spec.get("containers", []):
        container.setdefault("securityContext", {}).update(
            {"allowPrivilegeEscalation": False, "readOnlyRootFilesystem": True, "capabilities": {"drop": ["ALL"]}})
    return out

Write triage(pods) that returns a dict counting Pods by diagnosis using kubelab.pod_issue: the issue's reason, or "OK" when it returns None.

Hint

issue.reason if issue else "OK", then count with a dict or collections.Counter (convert it back to a plain dict).

Show solution
import kubelab

def triage(pods):
    counts = {}
    for pod in pods:
        issue = kubelab.pod_issue(pod)
        key = issue.reason if issue else "OK"
        counts[key] = counts.get(key, 0) + 1
    return counts

Quiz

Recap

  • A Pod is containers scheduled together, sharing an IP and volumes. Keep it to one app plus helpers.
  • Phases describe the Pod; states and reasons describe each container. CrashLoopBackOff is a restart back-off, not a cause.
  • Startup protects boots, readiness controls traffic, liveness restarts wedged processes.
  • Requests place Pods; limits cap them; requests and limits together decide the QoS class.
  • Init containers prepare; native sidecars accompany.
  • Write to restricted: non-root with a numeric UID, no escalation, no capabilities, seccomp.
  • Debug top-down: status, describe Events, logs --previous, then exec or debug.
